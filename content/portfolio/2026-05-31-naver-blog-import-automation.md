네이버 블로그에 오래 쌓아 둔 글을 지금 홈페이지로 옮기고 싶어졌다.

한 번에 전부 복사해서 옮길 수도 있겠지만, 글이 많아지면 문제도 같이 커진다. 카테고리가 잘못 들어갈 수 있고, 이미지가 깨질 수 있고, 공개하면 안 되는 글이 실수로 공개될 수도 있다. 그래서 이번 작업의 목표는 단순한 복사가 아니었다.

목표는 이렇게 정했다.

- 네이버 블로그 글을 자동으로 가져온다.
- 홈페이지의 최종 카테고리에 바로 넣는다.
- 하지만 처음에는 전부 비공개 초안으로 둔다.
- admin에서는 바로 확인할 수 있어야 한다.
- PC가 꺼져 있어도 매일 자동으로 조금씩 진행되어야 한다.
- 전체 이전이 어디까지 진행됐는지 로그로 확인할 수 있어야 한다.

## 처음 생각한 방식은 통째로 옮기기였다

처음에는 네이버 블로그의 카테고리를 분석해서 홈페이지 카테고리와 매칭한 뒤, 글을 통째로 옮기는 방식을 생각했다.

이 방식은 단순해 보인다. 네이버에 있는 `생각아카이브`, `오늘부터 독서`, `휴먼인텔리전스/심리`, `회사생활 365` 같은 카테고리를 홈페이지의 `essay`, `books`, `study`, `portfolio`에 연결하면 된다.

그런데 바로 통째로 옮기면 위험하다.

첫 번째 고민은 공개 여부였다.

네이버에서는 공개되어 있던 글이라도, 새 홈페이지에 바로 공개하는 것은 다른 문제다. 홈페이지는 지금 내가 새로 구성하는 공간이고, 글의 맥락도 달라진다. 그래서 옮긴 글은 사람이 한 번 확인하기 전까지 공개하지 않는 편이 낫다고 판단했다.

두 번째 고민은 카테고리였다.

네이버 카테고리와 홈페이지 카테고리는 1:1로 완벽하게 맞지 않는다. 예를 들어 네이버의 `기술적 지식`에 있는 글이 어떤 것은 공부 기록이고, 어떤 것은 실제로 만든 프로젝트 기록이다. 홈페이지에서는 전자는 `study`, 후자는 `portfolio`가 더 자연스럽다.

그래서 결론은 이렇게 바뀌었다.

통째로 옮기되, 바로 공개하지 않는다. 그리고 카테고리는 네이버 카테고리를 기준으로 1차 배치하되, 제목과 본문을 보고 일부 보정한다.

## RSS만으로는 부족했다

가장 먼저 확인한 것은 네이버 블로그 RSS였다.

`https://rss.blog.naver.com/coaching_blog.xml`로 접근하니 최근 글 목록은 가져올 수 있었다. RSS 안에는 제목, 링크, 요약, 날짜, 카테고리가 들어 있었다.

처음에는 이것만으로 충분할 수도 있겠다고 생각했다.

하지만 곧 한계가 보였다.

RSS는 최근 글을 확인하는 데는 좋지만, 전체 과거 글을 모두 안정적으로 가져오는 도구로 보기에는 부족했다. 이전해야 할 글이 수백 개라면 RSS만 보고 전체 이전 여부를 판단하기 어렵다.

그래서 네이버 블로그의 공개 API와 모바일 페이지를 같이 확인했다.

결국 공개 카테고리 목록은 다음 API에서 가져올 수 있었다.

```text
https://m.blog.naver.com/api/blogs/coaching_blog/category-list
```

전체 글 목록은 다음 API에서 페이지 단위로 가져올 수 있었다.

```text
https://m.blog.naver.com/api/blogs/coaching_blog/post-list?categoryNo=0&itemCount=30&page=1
```

여기서 중요한 값은 `logNo`였다.

네이버 블로그 글 주소가 이렇게 생겼다면,

```text
https://blog.naver.com/coaching_blog/224284673217
```

마지막 숫자 `224284673217`이 그 글의 고유 번호다. 이 번호를 기준으로 이미 옮긴 글인지 아닌지 판단할 수 있다.

이 지점에서 이전 방식이 조금 더 명확해졌다.

글 제목이 아니라 `logNo`를 기준으로 관리해야 한다. 제목은 바뀔 수 있고 중복될 수 있지만, `logNo`는 글을 식별하기에 적합하다.

## 최종 카테고리에 바로 넣되 draft로 숨기기로 했다

한때는 `content/naver-staging` 같은 임시 폴더에 글을 쌓는 방식을 생각했다.

이 방식은 안전하다. 아직 검토하지 않은 글을 공개 카테고리와 분리할 수 있기 때문이다.

그런데 실제 운영을 생각해 보니 문제가 있었다.

admin에서 글을 검토하고 다른 카테고리로 옮기는 작업이 쉽지 않다. 파일을 옮겨야 하고, 컬렉션도 달라진다. 결국 검토하기 편하려고 만든 staging이 오히려 운영을 불편하게 만들 수 있었다.

그래서 결정을 바꿨다.

처음부터 최종 카테고리 폴더에 넣는다.

다만 반드시 `draft: true`로 저장한다.

예를 들면 이런 방식이다.

```yaml
category: study
draft: true
source_blog_url: "https://blog.naver.com/coaching_blog/224284673217"
source_blog_category: "휴먼인텔리전스/심리"
import_review_note: "네이버 카테고리 '휴먼인텔리전스/심리' 기준으로 study에 배치."
```

이렇게 하면 admin에서는 `Study` 컬렉션 안에 글이 보인다. 하지만 공개 사이트에는 보이지 않는다.

여기서 중요한 보강이 하나 더 필요했다.

기존 홈페이지는 목록에서는 `draft` 글을 제외하고 있었지만, 개별 글 URL은 생성될 가능성이 있었다. 그러면 목록에는 안 보여도 주소를 직접 입력하면 접근할 수 있는 상태가 될 수 있다.

그래서 `src/pages/[category]/[slug].astro`에서 `draft: true` 글은 정적 페이지 경로 자체를 만들지 않도록 수정했다.

이 결정은 중요했다.

비공개 초안이라는 말이 진짜 의미를 가지려면, 목록에서만 숨기는 것이 아니라 개별 URL도 생성되지 않아야 한다.

## admin에서 보이게 하는 것이 핵심이었다

검증 과정에서 한 번 착각이 있었다.

로컬에 글 파일을 만들고 빌드까지 성공했기 때문에 작업이 끝났다고 생각할 수 있었다. 하지만 admin은 로컬 파일을 보는 것이 아니라 GitHub 저장소의 `main` 브랜치를 본다.

즉 로컬에만 있으면 admin에는 보이지 않는다.

이 지점에서 운영 기준이 다시 정리됐다.

자동 이전이 제대로 된 상태란 단순히 로컬 파일이 만들어진 상태가 아니다.

GitHub main에 커밋되고, admin에서 비공개 초안으로 확인 가능한 상태여야 한다.

그래서 가져온 검증 글인 `오늘의 문장`을 실제로 `content/study`에 넣고, GitHub에 push했다.

그 후 GitHub Actions 배포가 성공했고, admin 설정에도 `import_review_note` 필드가 반영된 것을 확인했다.

이제 가져온 글은 공개 사이트에는 보이지 않지만, admin에서는 확인할 수 있는 상태가 되었다.

## PC가 꺼져 있어도 돌아가야 했다

다음 고민은 예약 실행이었다.

Codex에도 예약 자동화 기능이 있지만, 로컬 PC가 꺼져 있으면 로컬 파일 시스템을 수정하는 작업은 안정적이지 않다. 모바일에서 Codex를 볼 수 있다고 해도, 내 PC의 `I:\AI for works\what-i-think` 폴더가 켜져 있는 것은 아니다.

그래서 예약 실행은 GitHub Actions로 처리하기로 했다.

GitHub Actions는 GitHub 서버에서 돌아간다. PC가 꺼져 있어도 작동한다. 그리고 이 홈페이지는 이미 GitHub Pages로 배포되고 있으니, 글을 가져오고 커밋하고 빌드하고 배포하는 흐름을 한 곳에서 처리하기 좋았다.

예약 시간은 매일 오전 6시 10분 KST로 잡았다.

```yaml
schedule:
  - cron: "10 21 * * *"
```

GitHub Actions의 cron은 UTC 기준이기 때문에, 한국 시간 06:10은 전날 21:10 UTC다.

처리 개수는 하루 3개로 정했다.

이유는 단순하다.

처음부터 많이 옮기면 검토해야 할 양이 너무 커진다. 자동 분류 규칙이 아직 완전히 검증되지 않았고, 이미지가 많은 글에서 어떤 문제가 생길지도 더 봐야 한다. 하루 3개면 1주일에 21개가 쌓인다. 검토하기에 부담이 적고, 문제가 생겨도 되돌리기 쉽다.

## 토큰을 거의 쓰지 않는 구조로 만들었다

이번 작업에서 또 하나 중요하게 생각한 것은 토큰 사용량이었다.

매일 글 3개를 옮길 때마다 LLM이 본문을 읽고 판단하게 만들면 비용과 토큰이 계속 든다. 그리고 매일 자동으로 반복되는 작업이라면 그 부담은 작아 보여도 누적된다.

그래서 import 스크립트는 LLM을 호출하지 않는다.

Node 스크립트가 네이버 공개 API와 공개 HTML을 읽고, 규칙 기반으로 처리한다.

카테고리 판단도 기본은 매핑표다.

- `오늘부터 독서`는 `books`
- `휴먼인텔리전스/심리`는 `study`
- `생각아카이브`는 `essay`
- `프로그래밍`은 기본적으로 `portfolio`
- `기술적 지식`은 내용에 따라 `study` 또는 `portfolio`

다만 제목과 본문에 `만들기`, `구현`, `프로젝트`, `배포`, `Codex`, `홈페이지` 같은 단어가 있으면 `portfolio`로 보정한다.

정밀한 판단은 사람이 admin에서 한다. 자동화는 초안을 적당한 위치에 넣어두는 역할만 한다.

이렇게 역할을 나누는 편이 낫다고 봤다.

기계는 반복 작업을 하고, 사람은 최종 공개 판단을 한다.

## 전체를 다 옮겼는지 확인하는 방법

마지막 고민은 완료 기준이었다.

매일 3개씩 옮기면 언젠가는 끝날 것이다. 그런데 끝났는지 어떻게 알 수 있을까?

처음에는 글을 하나씩 보면서 확인해야 하나 싶었다. 하지만 그럴 필요는 없다.

네이버의 전체 공개 글 목록에서 모든 `logNo`를 가져오고, 이미 처리한 `logNo` 목록과 비교하면 된다.

그래서 `content/naver-import-state.json`에 처리한 글 번호를 저장한다.

```json
{
  "importedLogNos": [
    "224287569845",
    "224284673217"
  ]
}
```

그리고 `NAVER_IMPORT_REPORT.md`에 진행률을 남기도록 했다.

상태 점검 명령은 다음과 같다.

```bash
npm run import:naver -- --status
```

실행하면 이런 정보가 남는다.

```text
naver_public_posts_scanned: 680
imported_or_skipped: 2
remaining: 678
```

`remaining`이 0이 되면 공개 글 기준으로 이전이 끝난 것이다.

여기서 `imported_or_skipped`라고 표현한 이유도 있다. 이미 홈페이지에 있던 글처럼 실제 파일은 만들지 않았지만 다시 가져오면 안 되는 글이 있다. 그런 글은 import된 것은 아니지만 처리 완료로 봐야 한다.

그래서 상태 파일에는 그런 글의 `logNo`도 남겨 둔다.

## 실제로 가져온 첫 검증 글

처음 검증에서 `홈페이지 인공지능으로 만들어 버리기`를 가져왔는데, 이 글은 이미 what-i-think에 있던 글이었다. 그래서 검증용 draft 파일은 제거했다.

다만 그 네이버 글의 `logNo`는 상태 파일에 남겼다. 그래야 자동화가 다시 같은 글을 가져오지 않는다.

그 다음 실제 검증용으로 가져온 글은 `오늘의 문장`이었다.

이 글은 다음 파일로 들어갔다.

```text
content/study/2026-05-13-오늘의-문장.md
```

상태는 `draft: true`다.

빌드 결과 공개 페이지에는 나오지 않았고, admin에서는 `Study` 컬렉션에서 확인할 수 있는 상태가 되었다.

## 결과

이번 작업으로 만들어진 흐름은 다음과 같다.

1. GitHub Actions가 매일 오전 6시 10분에 실행된다.
2. 네이버 블로그 공개 글 목록을 최신순으로 가져온다.
3. `content/naver-import-state.json`을 보고 이미 처리한 글은 건너뛴다.
4. 아직 처리하지 않은 글 3개를 가져온다.
5. 네이버 카테고리와 본문 키워드를 기준으로 홈페이지 카테고리를 정한다.
6. 최종 카테고리 폴더에 `draft: true` Markdown으로 저장한다.
7. `import_review_note`에 카테고리 판단 이유를 남긴다.
8. `NAVER_IMPORT_REPORT.md`에 오늘 처리 결과와 전체 진행률을 남긴다.
9. 빌드가 통과하면 GitHub에 커밋하고 GitHub Pages에 배포한다.

이제 내가 할 일은 admin에 들어가서 매일 쌓이는 초안을 검토하는 것이다.

공개할 글은 `비공개 초안`을 끄면 된다. 카테고리가 틀렸다면 수정하면 된다. 본문이 어색하면 조금 다듬으면 된다.

자동화가 모든 것을 결정하지 않는다. 자동화는 반복 작업을 줄이고, 사람이 판단해야 할 일을 더 잘 보이게 만든다.

그 정도가 지금 이 홈페이지에 가장 맞는 자동화 수준이라고 생각한다.

## 배운 점

이번 작업에서 가장 중요했던 것은 “자동화 범위”를 정하는 일이었다.

글을 자동으로 가져오는 것은 쉽다. 하지만 공개까지 자동으로 하는 것은 다른 문제다. 특히 개인 블로그 글은 그때의 맥락과 지금의 맥락이 다를 수 있다.

그래서 이번 자동화는 일부러 끝까지 가지 않았다.

가져오기까지만 자동화하고, 공개 판단은 남겨 두었다.

또 하나 배운 점은 운영 구조가 중요하다는 것이다.

로컬에서 잘 되는 것과 admin에서 보이는 것은 다르다. 파일이 생성되는 것과 GitHub main에 올라가는 것도 다르다. draft가 목록에서 숨겨지는 것과 개별 URL이 생성되지 않는 것도 다르다.

작은 차이처럼 보이지만 실제 운영에서는 이런 차이가 문제를 만든다.
