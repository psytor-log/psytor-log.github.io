프롬프트를 만들어 판매해 보자는 생각으로 시작했다.

처음에는 신입사원, 대학생, 취업준비생, 1인기업가에게 필요한 프롬프트를 각각 15개씩 만들면 된다고 생각했다. 하지만 작업을 진행할수록 프롬프트 문장만 60개 모아 놓는 것으로는 상품이 되기 어렵다는 사실이 분명해졌다.

무료로 질문할 수 있는 AI와 경쟁하려면, 구매자가 **무엇을 입력하고, 어떤 형식으로 받고, 결과를 어떻게 점검하고 개선할지**까지 설계해야 했다.

## 문제

범용 프롬프트는 만들기 쉽다.

“이메일을 써 줘”, “자소서를 첨삭해 줘”, “마케팅 아이디어를 만들어 줘” 같은 요청은 몇 줄이면 작성할 수 있다. 문제는 이런 프롬프트를 유료로 판매할 이유가 약하다는 점이다. 사용자가 직접 AI에게 물어도 비슷한 결과를 얻을 수 있기 때문이다.

또 하나의 문제는 수량이었다. 4개 대상에게 15개씩 만들려면 총 60개가 필요하다. 빠르게 채우는 데 집중하면 제목만 다르고 본문은 거의 같은 프롬프트 묶음이 되기 쉽다.

그래서 목표를 “프롬프트 60개 작성”이 아니라 **대상별로 바로 사용할 수 있는 판매 패키지 4개 제작**으로 바꿨다.

## 목표

대상별 상품 하나가 다음 구성을 갖추도록 했다.

- 대상별 필수 프롬프트 15선
- 초보자를 위한 사용 설명서
- PDF 설명서
- 크몽 판매용 상세페이지
- 프롬프트별 품질 점검과 최종 검수 기록

각 프롬프트는 독립적으로 복사해서 사용할 수 있어야 했다. 사용자가 처음 입력할 정보, 원하는 출력 형식을 고르는 질문, 결과 품질을 확인하는 기준, 결과를 다시 개선하는 문장도 반드시 포함하도록 했다.

## 접근 방식 — 바로 쓰지 않고 먼저 고르기

처음부터 최종 15개를 만들지 않았다.

먼저 각 대상이 반복해서 겪는 문제와 처리 업무를 50개 이하로 정리했다. 비슷한 작업을 묶고, 텍스트 프롬프트로 해결하기 어려운 일과 상품 가치가 낮은 일은 제외했다.

이 과정을 거쳐 대상별 후보를 만들고, 실제 상품에 넣을 항목을 선택했다.

예를 들어 신입사원에게는 업무 이메일, 보고서, PPT 구조, 우선순위, 긴 사내 문서 요약이 남았다. 취업준비생에게는 경험 정리, STAR 스토리, 자소서 맞춤화, 1분 자기소개, 모의면접이 남았다. 1인기업가는 고객 정의, 가격 전략, 콘텐츠, 판매 페이지, 협상과 자동화 중심으로 구성했다.

선별 과정을 먼저 둔 덕분에 단순히 15개를 채우는 대신, 대상이 실제로 반복해서 사용할 만한 작업을 고를 수 있었다.

## 프롬프트를 하나의 작은 도구로 만들기

최종 프롬프트에는 공통적으로 아홉 가지 구성을 넣었다.

1. 제목
2. 이런 상황에서 사용
3. 사용자가 먼저 준비할 입력값
4. 출력 형식 선택 질문
5. 복사용 최종 프롬프트
6. 출력 예시 구조
7. 품질 점검 문장
8. 결과 개선 요청 문장
9. 사용 팁

여기에 각 주제의 고유 방법론을 추가했다.

예를 들어 업무 이메일 프롬프트에는 수신자와 권한 수준을 먼저 판단하고, 제목-요청-근거-기한-후속 행동 순서로 작성하도록 했다. STAR 경험 스토리는 Situation 15%, Task 15%, Action 50%, Result 20% 비중으로 구성했다. 모의면접 프롬프트는 보고서를 한 번 생성하는 방식이 아니라, 질문 하나를 제시하고 답변을 기다린 뒤 평가와 다음 질문으로 이어지는 대화형 구조로 바꿨다.

검수 과정에서 처음 만든 63개 프롬프트가 지나치게 같은 템플릿처럼 보인다는 지적도 나왔다. 내부 상품 가치 등급이 판매본에 노출되어 있었고, 발표자료 프롬프트에 이메일용 출력 선택지가 들어간 오류도 있었다.

이 문제를 반영해 대상별 정확히 15개, 총 60개로 정리했다. 모든 프롬프트에 주제별 방법론을 넣고, 중복과 내부 메타데이터를 제거했다.

## 사용 설명서와 PDF 자동화

좋은 프롬프트를 만들어도 구매자가 사용하지 못하면 상품 가치가 없다.

그래서 대상별 설명서에는 다음 내용을 넣었다.

- 이 자료가 필요한 사람
- 사용 전 준비사항
- 입력값 작성법
- 출력 형식 선택법
- 복사해서 사용하는 방법
- 좋은 답변을 얻기 위한 수정 방법
- 자주 발생하는 문제와 해결법
- 프롬프트 15개별 사용 가이드
- 예시 사용 시나리오

설명서는 Markdown으로 관리하고, Node.js 스크립트로 PDF를 만들도록 했다. `marked`로 Markdown을 HTML로 바꾸고 Playwright Chromium으로 A4 PDF를 출력한다.

```powershell
npm.cmd run build:pdf
```

한글이 깨지지 않도록 UTF-8과 한글 폰트 우선순위를 지정했다. 현재 대상별 PDF 4개를 같은 명령으로 다시 생성할 수 있다.

## 크몽 상세페이지 만들기

상세페이지는 “프롬프트가 15개 있습니다”라고 설명하는 데 그치지 않도록 했다.

구매자가 자신의 상황을 바로 떠올릴 수 있도록 대상별 목록, 사용 전후 비교, 긴 프롬프트 사례, 구매 후 사용 단계, FAQ를 넣었다. 수익, 합격, 업무 성과를 보장하는 표현은 사용하지 않았다. 이 상품이 초안 작성과 준비 과정의 시행착오를 줄이는 도구라는 점을 명확히 했다.

대상별 HTML은 외부 의존성 없는 단일 파일로 만들었다. 이미지가 아직 없더라도 레이아웃이 깨지지 않도록 자리표시자를 표시한다. 실제 판매 전에는 대상별 이미지 12개를 생성하고 최종 화면을 확인해야 한다.

## 결과

최종 산출물은 다음과 같다.

- 대상별 프롬프트 15개, 총 **60개**
- 대상별 Markdown 사용 설명서 **4개**
- 대상별 PDF 사용 설명서 **4개**
- 대상별 크몽 상세페이지 **4개**와 통합형 페이지
- 프롬프트 품질 점검 **60건**
- 리서치, 선별 기록, 최종 검수 보고서
- 프롬프트 생성과 PDF 변환을 다시 실행할 수 있는 스크립트

결과적으로 하나의 긴 문서가 아니라, 대상별로 분리해 판매하고 수정할 수 있는 디지털 상품 패키지가 만들어졌다.

## 배운 점

첫 번째로 배운 것은 **프롬프트의 길이가 상품 가치를 만들지는 않는다**는 점이다. 긴 문장이 반복되면 구매자는 금방 같은 템플릿이라는 사실을 알아챈다. 각 작업이 가진 고유한 판단 순서와 점검 기준이 들어가야 한다.

두 번째는 **사용법도 상품의 일부**라는 점이다. AI를 잘 쓰는 사람에게는 프롬프트 본문만 있어도 충분할 수 있다. 하지만 처음 쓰는 구매자에게는 입력값을 어떻게 준비하고 결과를 어떻게 고칠지가 더 중요하다.

세 번째는 **검수가 생성보다 중요하다**는 점이다. 처음에는 63개가 만들어졌지만 최종 검수를 거쳐 60개가 됐다. 출력 형식 오류, 어색한 문장, 중복, 내부 메타데이터 노출도 검수 과정에서 발견했다.

마지막으로, 판매 패키지는 콘텐츠만으로 끝나지 않는다. PDF를 다시 만들 수 있는 스크립트, 상세페이지, 이미지, 광고 문구, 품질 근거까지 함께 있어야 실제 운영 가능한 상품에 가까워진다.

## 다음 개선 방향

- 상세페이지에 사용할 대상별 이미지 12개 생성과 배치
- 실제 이미지가 포함된 데스크톱·모바일 화면 최종 검수
- 대상별 가격과 판매 옵션 결정
- 사용 설명서뿐 아니라 프롬프트 본문까지 포함한 구매자용 통합 PDF 검토
- 실제 구매자 사용 후 반복적으로 막히는 지점과 결과 품질 기록

아직 판매 결과는 없다. 지금까지 만든 것은 판매 가능한 형태에 가까워진 첫 패키지다. 다음 단계에서는 프롬프트 수보다 실제 구매자가 어느 작업에서 시간을 줄였고, 어느 부분에서 다시 막혔는지를 확인해야 한다.
